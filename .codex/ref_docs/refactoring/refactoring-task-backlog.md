## 1. 백로그 사용 방법 (Task 상태 갱신 규칙)

### 1.1 상태 표기

각 Task의 상태는 **Task ID 셀 앞에 마커를 붙여** 갱신한다 (표 컬럼 구조는 변경하지 않는다).

| 마커 | 상태 | 갱신 규칙 |
|---|---|---|
| (없음) | 대기 | 초기 상태. 선행 작업이 모두 ✅가 되기 전에는 착수 금지 |
| 🔵 | 진행 중 | 착수 시 표기. 같은 파일을 다루는 Task는 동시에 1개만 🔵 가능 (특히 `Simulation2Page.tsx`/`AdminPage3.tsx`는 직렬 진행 — dependency-aware-sequence 4.5) |
| ✅ | 완료 | **완료 조건의 검증 명령어/수동 확인을 모두 통과**하고, 해당 commit hash를 Task 행 끝(완료 조건 셀)에 추기한 뒤 표기 |
| ⏸ | 보류 | "확인 필요" 항목이 해소되지 않아 진행 불가한 경우. 보류 사유와 차단 항목을 셀에 추기 |
| ❌ | 제외 | 수행하지 않기로 결정된 경우. 사유 필수 (3장 보류/제외 표로 이동) |

### 1.2 운영 규칙

1. **선행 작업 우선**: `선행 작업` 컬럼의 RF-TASK가 모두 ✅이기 전에는 착수하지 않는다. 선행이 ⏸이면 본 Task도 ⏸ 후보다 (dependency-aware-sequence 4.4의 alias 우회 등 대안이 명시된 경우 예외).
2. **1 Task = 독립 commit (이상)**: revert 가능 단위를 유지한다. 한 Task를 여러 commit으로 쪼개는 것은 허용, 여러 Task를 한 commit에 합치는 것은 금지 (추론).
3. **검증 명령어**: 완료 조건의 명령어는 package.json에서 확인된 실제 스크립트만 사용한다 — `npm run lint` / `npm run build` / `npm run test:run` / `npm run test:coverage` / `npm run test:boundaries` / `npm run test:circular` / `npm run test:route-smoke` / `npm run test:strict-scope` / `npm run test:strict-scope-coverage` / `npm run test:diff-check` / `npm run test:w12-guards` / `npm run test:w12-full`. `npx tsc --noEmit`은 root tsconfig baseline 후보 명령(확인 필요, strict off라 검출력 약함 — RF-FINDING-038)이다.
4. **수동 검증**: Playwright MCP 사용. local `http://localhost:3000`, production(시뮬레이션 앱) `https://pfm.cmsl-kookmin.com/simulation2`.
5. **게시판 앱(cmsl*/board/CMS, Supabase) 수정 지양 규칙**: 게시판 앱 영역 Task(Phase 0 ③④, Phase 2 RF-003 계열, Phase 3 RF-020/021/037, Phase 5 RF-044/013/012, Phase 6 RF-005/006/007/009 일부 등)는 착수 전 사용자 확인을 받고, 결함 수정/리팩토링 근거와 변경 범위를 커밋·PR에 명시하며 최소 수정으로 진행한다.
6. **Phase 경계 → 트랙 게이트**: Wave 실행(`refactoring-execution-order.md`) 시에는 Phase 단위 게이트 대신 **트랙별 진입 조건**(같은 문서 설계 원칙 5·Wave 표)을 적용한다 — CMS 승인 지연이 PFM 트랙을 막지 않도록 하기 위함. Wave 설계를 사용하지 않는 예외적 실행에서만 "한 Phase의 필수 Task(P3 검토성 Task 제외)가 모두 ✅여야 다음 Phase 착수" 원칙으로 복귀한다. Phase 간 병렬은 dependency-aware-sequence 3장의 병렬 그룹(그룹 A: PFM / 그룹 B: CMS / 그룹 C: 독립 소형) 범위에서 허용 (추론). **명칭 주의**: 이 그룹 A/B/C는 execution-order의 트랙 S/A/C/Q와 다른 체계다 (특히 그룹 C(독립 소형) ≠ 트랙 C(CMS·게시판, 승인 게이트 필수)).
7. **민감 영역 변경 시**: phased-refactoring-plan Phase 0의 민감 영역 표(apiClient token refresh, `lib/api/http.ts` WS helper, Simulation2Page WS lifecycle, AdminPage3 invalidation/권한, Supabase delete/upload 순서, `apiRequest<T>` 기본값, admin DTO 통합, parameter mapper)에 해당하면 해당 Phase 문서의 위험 요소/롤백 기준을 먼저 읽고 착수한다.
8. **실행 순서**: 실행 순서는 `refactoring-execution-order.md`의 Wave 설계를 우선 적용한다 (Phase 번호 순서와 다를 수 있음).
